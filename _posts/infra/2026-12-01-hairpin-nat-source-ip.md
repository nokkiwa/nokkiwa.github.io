[Redis 침해 글](/security/2026/11/24/redis-replicaof-intrusion.html)을 쓰면서 설명을 미뤄 둔 게 하나 있다. Redis에 붙어 있던 클라이언트 목록을 봤을 때, 같은 서버에서 도는 내 앱의 연결이 전부 **공유기 내부 주소**에서 온 것으로 찍혀 있었다. 앱은 분명 이 서버 안에 있는데, Redis 입장에서는 공유기가 접속한 것처럼 보였다.

원인은 앱이 Redis 주소를 **공인 IP**로 적어 둔 데 있었다. 같은 집 안에서 공인 IP로 접속하면 패킷이 공유기까지 나갔다가 되돌아오는데, 이걸 헤어핀 NAT(NAT 루프백)라고 부른다. 말로만 알던 걸 이번에 직접 찍어 봤다.

## 실험: 같은 nginx에 네 가지 길로 접속

서버에서 돌고 있는 nginx에, 서버 자신이 네 가지 주소로 요청을 보냈다. 요청마다 User-Agent에 꼬리표를 달아 두고, nginx 접속 로그에서 각 요청의 출발지 IP를 꺼냈다.

```bash
UA="hairpin-test-$(date +%s)"
curl -sk -o /dev/null -A "$UA-pub" https://<공인IP>/
curl -sk -o /dev/null -A "$UA-lan" https://<서버내부IP>/
curl -sk -o /dev/null -A "$UA-lo"  https://127.0.0.1/
docker run --rm curlimages/curl:8.11.1 -sk -o /dev/null -A "$UA-ctr" https://<서버내부IP>/

grep "$UA" /var/log/nginx/access.log | awk '{print $1, $NF}'
```

결과는 이랬다. 실제 주소는 가렸다.

| 접속한 주소 | nginx가 본 출발지 |
|---|---|
| 공인 IP | **공유기 내부 IP** |
| 서버 내부 IP | 서버 내부 IP (자기 자신) |
| 127.0.0.1 | 127.0.0.1 |
| 컨테이너에서 서버 내부 IP로 | `172.17.0.x` (Docker 브리지 주소) |

같은 기계에서 같은 서버로 보낸 요청인데, 어떤 주소로 접속했느냐에 따라 출발지가 네 가지로 달라진다. 공인 IP로 접속한 요청만 공유기 주소로 찍혔다.

## 왜 공유기 주소로 바뀌나

공인 IP는 공유기가 들고 있는 주소다. 그래서 서버가 공인 IP로 요청을 보내면 패킷은 일단 공유기로 간다. 공유기는 "이 주소의 443번은 내부 서버로 넘긴다"는 포트포워딩 규칙을 보고 목적지를 서버 내부 IP로 바꿔 돌려보낸다. 여기까지는 바깥에서 들어오는 요청과 같다.

차이는 출발지다. 바깥 손님이라면 출발지를 그대로 두면 된다. 서버의 응답은 공유기를 거쳐 나가면서 다시 공인 IP로 바뀌기 때문이다. 그런데 손님이 같은 집 안에 있으면 문제가 생긴다. 출발지를 그대로 두면 서버는 응답을 공유기를 거치지 않고 손님에게 바로 보낸다. 손님은 공인 IP에 요청을 보냈는데 엉뚱한 내부 주소에서 답이 오니 그 응답을 버린다.

그래서 헤어핀을 지원하는 공유기는 **출발지까지 자기 주소로 바꿔서** 서버에게 넘긴다. 그러면 서버의 응답이 반드시 공유기로 돌아오고, 공유기가 주소를 원래대로 되돌려 손님에게 전해 준다. 위 실험에서 공인 IP로 보낸 요청이 공유기 주소로 찍힌 게 바로 이 과정이다.

참고로 바깥에서 들어오는 연결은 출발지가 바뀌지 않는다. Redis 침해 글에서 SSH 대입을 시도하던 상하이 IP가 서버의 연결 목록에 그대로 보였던 것도 그래서다.

## 이게 실제로 일으킨 문제 세 가지

이론으로만 보면 "출발지가 좀 바뀌는구나" 하고 넘어갈 일이다. 그런데 이 서버에서는 실제로 이것 때문에 꼬인 게 세 가지 있었다.

**첫째, 방화벽의 "내부망만 허용" 규칙이 이 연결도 통과시켰다.** MySQL 포트는 ufw로 사설망 대역(`192.168.0.0/16` 등)에서만 받도록 해 두었다. 그런데 공인 IP로 DB에 붙던 앱도 잘 동작했다. 출발지가 공유기 내부 주소, 즉 사설망 주소로 바뀌어 들어왔기 때문이다. Docker 포트 앞에 둔 `DOCKER-USER` 규칙도 사설망을 통과시키도록 짰기 때문에 같은 이유로 통과했다. 덕분에 앱이 끊기지 않았지만, 바꿔 말하면 내가 "내부"라고 믿은 연결 중 일부는 실제로 공유기를 한 바퀴 돌아온 연결이었다.

**둘째, Redis 보호 모드를 켤 수 없었다.** Redis의 보호 모드는 비밀번호가 없을 때 `127.0.0.1`에서 온 연결만 받는다. 앱의 연결이 공유기 주소로 들어오니 보호 모드를 켜면 앱이 끊긴다. 원래 컨테이너에 보호 모드가 꺼져 있던 것도 아마 같은 이유였을 것이다. 결과적으로 보호 모드가 꺼진 채 포트포워딩까지 열려 있었고, 그게 침해로 이어졌다.

**셋째, 공유기 포트포워딩을 지울 수 없었다.** 앱이 공인 IP로 접속하는 한, 그 앱이 쓰는 포트는 공유기에서 포워딩이 살아 있어야 한다. 바깥에서 쓸 일이 없는 DB나 Redis 포트를 순전히 내 앱 때문에 인터넷에 열어 둔 셈이었다.

## 속도 차이는 얼마나 날까

내친김에 TCP 연결에 걸리는 시간도 30번씩 재 봤다.

```bash
for i in $(seq 30); do
  curl -sk -o /dev/null -w '%{time_connect}\n' https://<공인IP>/
done | sort -n
```

| 접속 주소 | 중앙값 | 상위 10% | 최대 |
|---|---|---|---|
| 공인 IP (헤어핀) | 0.87ms | 0.95ms | 1.02ms |
| 서버 내부 IP | 0.44ms | 0.48ms | 0.75ms |

공유기까지 한 번 다녀오는 만큼 두 배쯤 느리다. 공유기와의 왕복 시간(`ping`)이 평균 0.33ms였으니 거의 그만큼 더해진 것이다. 1ms도 안 되는 차이라 체감할 일은 없다. 속도보다는 앞의 세 가지 문제, 그리고 **공유기가 재부팅되거나 통신사가 공인 IP를 바꾸면 앱이 바로 끊긴다**는 점이 훨씬 크다. 가정용 인터넷의 공인 IP는 대부분 고정이 아니다.

## 고친 방법: 같은 서버 안에서는 내부 주소로

같은 서버에서 도는 앱이 같은 서버의 DB에 붙을 때는 공인 IP를 쓸 이유가 없다. 그 앱의 DB 주소를 서버 내부 IP로 바꿨다. 스프링 부트 앱이라 이미지를 다시 빌드하지 않고 환경변수 하나로 설정 파일 값을 덮어쓸 수 있었다.

```bash
docker run -d ... \
  -e 'SPRING_DATASOURCE_URL=jdbc:mysql://<서버내부IP>:3306/<DB이름>?serverTimezone=Asia/Seoul' \
  <이미지>
```

컨테이너를 다시 띄우고 MySQL 쪽에서 연결 목록을 보니, 이 앱의 출발지가 공유기 주소에서 `172.17.0.x`(컨테이너 주소)로 바뀌어 있었다. 공유기를 거치지 않는다는 뜻이다. 이제 이 앱 때문에 공유기에서 DB 포트를 열어 둘 이유는 없어졌다.

빌드 서버(Jenkins)가 배포할 때 설정 파일을 새로 만드는 구조라서, 거기 적힌 DB 주소도 같이 바꿨다. 이걸 빼먹으면 다음 배포 때 다시 공인 IP로 돌아간다.

## 정리

- 집 안에서 공인 IP로 접속하면 출발지가 **공유기 내부 주소**로 바뀐다. 실험 한 번이면 확인할 수 있다.
- 그래서 "사설망만 허용" 규칙은 공유기를 돌아온 연결도 통과시킨다. 내부라고 믿은 연결이 실제로 내부가 아닐 수 있다.
- 같은 서버나 같은 집 안의 서비스끼리는 내부 주소(또는 컨테이너 네트워크)로 붙게 하자. 그래야 공유기 포트포워딩을 최소로 줄일 수 있다.

내 서버에서 이런 연결이 있는지 보려면, DB나 캐시의 클라이언트 목록에서 공유기 내부 주소를 찾아보면 된다. Redis라면 `redis-cli CLIENT LIST`, MySQL이라면 `SHOW PROCESSLIST`의 `Host` 열이다. 거기 공유기 주소가 보인다면, 어딘가에 공인 IP로 접속하는 앱이 있다는 뜻이다.
