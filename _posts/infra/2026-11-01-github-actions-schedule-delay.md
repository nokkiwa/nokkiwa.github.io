이 블로그는 GitHub Pages에 Jekyll로 올라가 있다. 글을 미리 써두고 날짜가 되면 공개되게 하고 싶었는데, Jekyll은 빌드 시점보다 미래 날짜인 글을 건너뛴다. 그러니 **날짜가 바뀐 뒤에 누군가 빌드를 한 번 돌려줘야** 글이 나간다. 그 역할을 GitHub Actions의 `schedule`에 맡겼다.

결론부터 말하면 잘 동작은 한다. 다만 cron에 적은 시각에 도는 일은 거의 없었다. 한 달 동안 쌓인 실행 기록으로 얼마나 밀리는지 재봤다.

### 1. 처음 설정: 매일 09:05 KST

```yaml
on:
  push:
    branches: ["main"]
  schedule:
    - cron: "5 0 * * *"   # UTC 00:05 = KST 09:05
```

cron은 UTC 기준이라 한국 시간 9시 5분은 `5 0`이다. 글 날짜를 09:00으로 맞춰두고 5분 뒤 빌드하면 되겠다고 생각했다.

첫날, 낮 12시가 넘도록 글이 안 올라왔다. Actions API로 실행 목록을 보니 `event: schedule`인 실행이 **아예 없었다**. 늦은 게 아니라 그날 실행 자체가 없었다.

```bash
curl -s "https://api.github.com/repos/<owner>/<repo>/actions/runs?event=schedule&per_page=5"
```

GitHub 문서에도 이렇게 적혀 있다.

> 부하가 높은 시간대에는 schedule 이벤트가 지연될 수 있다. 매시 정각이 부하가 높은 시간이다. 부하가 충분히 높으면 대기 중인 작업 일부가 버려질 수 있다.

정각 근처는 전 세계 cron이 몰리는 시간이다. 00:05는 정각에서 너무 가까웠다.

### 2. 바꾼 설정: 하루 3번, 23분

```yaml
  schedule:
    - cron: "23 0,8,16 * * *"   # KST 09:23 · 17:23 · 01:23
```

- 정각을 피해서 23분으로 옮겼다.
- 한 번이 버려져도 같은 날 다른 실행이 받아주도록 하루 세 번으로 늘렸다. 빌드는 1분 남짓이라 부담이 없다.

### 3. 한 달 실측

설정을 바꾼 9월 26일부터 10월 26일까지 `schedule` 실행 기록을 전부 받아서, 각 실행이 예정 시각보다 얼마나 늦게 시작했는지 계산했다.

| 항목 | 값 |
|---|---|
| 예정된 실행 | 90번 |
| 실제 실행 | 87번 (성공 86, 실패 1) |
| 지연 중앙값 | **약 4시간 50분** |
| 지연 90% 지점 | 약 6시간 30분 |
| 최대 지연 | 약 7시간 40분 |
| 1시간 안에 시작 | 2번 |
| 3시간 넘게 지연 | 78번 |

예정 시각별로 나눠봐도 차이는 있지만 전부 몇 시간 단위다.

| 예정 (KST) | 지연 중앙값 |
|---|---|
| 09:23 | 약 5시간 10분 |
| 17:23 | 약 5시간 40분 |
| 01:23 | 약 3시간 40분 |

- **빠진 실행 3번**: 하루 세 번이어야 하는데 두 번만 돈 날이 사흘 있었다. 하루 여러 번으로 둔 덕분에 글 공개에는 지장이 없었다.
- **실패 1번**: 빌드는 성공했고 배포 단계에서 GitHub Pages 서버가 502를 돌려줬다. 다음 실행에서 정상으로 돌아왔다.
- 결과적으로 09:00으로 예약한 글이 실제로 공개된 시각은 **오후 1시 41분 ~ 밤 10시 13분, 중앙값 오후 2시 35분**이었다.

### 4. 쓸 때 알아둘 것

- **분 단위 정확도가 필요하면 schedule을 쓰면 안 된다.** 몇 시간 밀리는 게 평소 모습이다. "그날 안에만 돌면 된다" 정도의 작업에 맞다.
- **정각과 정각 직후는 피한다.** 문서가 직접 경고하는 시간대다.
- **중요하면 하루 여러 번 돌게 하고, 작업은 여러 번 돌아도 결과가 같게 만든다.** Jekyll 재빌드는 몇 번을 돌려도 결과가 같아서 이 조건에 딱 맞았다.
- **공개 저장소는 60일 동안 활동이 없으면 예약 워크플로가 자동으로 꺼진다.** 글을 몇 달치 예약해두고 커밋을 안 하면 중간에 멈출 수 있다. 꺼지면 Actions 탭에서 다시 켜야 한다.
- schedule은 **기본 브랜치의 최신 커밋**으로 돈다. 다른 브랜치에 넣은 workflow 파일은 무시된다.

### 정리

GitHub Actions의 cron은 "이 시각에 실행"이 아니라 "이 시각 이후 언젠가 실행"에 가깝다. 이 블로그에선 한 달 동안 중앙값 4시간 50분이 밀렸고, 정각 근처로 잡은 첫 설정은 아예 실행되지 않은 날도 있었다. 예약 발행처럼 하루 단위면 충분한 일이라면 정각을 피해 하루 여러 번 돌리는 것으로 해결된다.
