Spring Boot로 API를 만들면서 반복해서 마주친 오류 세 가지를 모아 정리했다.
셋 다 메시지만 보면 뭐가 문제인지 감이 안 오는데, 원인을 알고 나면 전부 "JPA가 대신 해주던 일"과 관련이 있었다.

검색하면 해결 코드는 금방 나오지만 왜 그런지가 잘 안 나와서, 다음에 또 만났을 때를 위해 원인까지 같이 적어 둔다.

<br/>

## 1. SQL Error 1064 - 예약어와 겹친 엔티티 이름

### 증상

애플리케이션은 뜨는데 특정 엔티티에 쿼리가 나갈 때 문법 오류가 난다.

```
java.sql.SQLSyntaxErrorException:
You have an error in your SQL syntax; check the manual that corresponds to
your MySQL server version for the right syntax to use near ...
```

`1064`는 MySQL/MariaDB가 **SQL 문법을 파싱하지 못했을 때** 내는 범용 에러 코드다.
내가 직접 쓴 쿼리가 없는데도 나서 한참을 헤맸다.

### 원인

JPA는 엔티티 이름과 필드 이름을 그대로 테이블명·컬럼명으로 바꿔 쿼리를 만든다.
그런데 그 이름이 DB의 **예약어**와 겹치면, DB 입장에서는 테이블 이름이 아니라 문법 키워드로 읽힌다.

예를 들어 `Order`, `Group`, `Rank`, `Key`, `Desc` 같은 이름이 그렇다.
`select ... from order`가 나가면 DB는 `order`를 `ORDER BY`의 그 order로 해석해서 문법이 깨진다.

내가 쓴 쿼리가 아니라 **하이버네이트가 생성한 쿼리**에서 터지기 때문에, 코드를 아무리 봐도 원인이 안 보인다.

### 해결

`application.properties`에 아래를 추가하면 하이버네이트가 생성하는 모든 식별자를 따옴표로 감싼다.

```properties
spring.jpa.properties.hibernate.globally_quoted_identifiers=true
```

이러면 `select ... from "order"`처럼 나가서 예약어와 부딪히지 않는다.

### 다시 겪지 않으려면

이 설정은 **전체**에 적용되는 방식이라, 이미 굴러가는 프로젝트에 중간에 켜면 기존 쿼리에 영향이 갈 수 있다.
문제가 되는 엔티티가 하나뿐이라면 이름을 바꿔 주는 쪽이 부작용이 적다.

```java
@Entity
@Table(name = "orders")   // 예약어 order 대신
public class Order { ... }
```

애초에 엔티티 이름을 지을 때 예약어를 피하는 게 제일 낫다.

## 2. cannot deserialize from Object value - 기본 생성자가 없을 때

### 증상

`POST`로 JSON을 받는 API에서 요청이 들어오는 순간 500이 난다.

```
cannot deserialize from Object value (no delegate- or property-based creator)
```

### 원인

Spring Boot는 요청 본문의 JSON을 객체로 바꿀 때 **Jackson**을 쓴다.
Jackson의 기본 동작은 이렇다.

1. 인자 없는 생성자로 빈 객체를 만든다
2. JSON의 각 필드를 setter나 리플렉션으로 채운다

그런데 클래스에 `@AllArgsConstructor`만 붙어 있거나 직접 만든 생성자만 있으면, 자바는 기본 생성자를 자동으로 만들어 주지 않는다.
그래서 1번 단계에서 바로 막힌다. 메시지의 "no delegate- or property-based creator"가 정확히 **객체를 만들 방법이 없다**는 뜻이다.

### 해결

받는 쪽 DTO에 기본 생성자를 만들어 준다.

```java
@Getter
@NoArgsConstructor   // 이것
@AllArgsConstructor
public class SignUpRequest {
    private String email;
    private String password;
}
```

Lombok을 안 쓴다면 `public SignUpRequest() {}`를 직접 넣어도 같다.

### 다시 겪지 않으려면

- 요청을 받는 DTO에는 습관적으로 `@NoArgsConstructor`를 붙여 둔다.
- 응답으로만 나가는 DTO는 직렬화(객체 → JSON)라 방향이 반대이므로 기본 생성자가 없어도 된다. 그래서 응답은 되는데 요청만 터지는 상황이 생긴다.
- `record`나 불변 객체로 받고 싶다면 `@NoArgsConstructor` 대신 생성자에 `@JsonCreator`와 `@JsonProperty`를 붙이는 방법도 있다.

## 3. query did not return a unique result - 하나인 줄 알았던 결과

### 증상

조회 중에 아래 예외가 뜬다.

```
query did not return a unique result: 3
```

뒤의 숫자는 실제로 조회된 행의 개수다. 3개가 나왔다는 뜻이다.

### 원인

리턴 타입을 단일 객체로 선언한 메서드는 결과가 **정확히 0개나 1개**일 때만 동작한다.

```java
Optional<Member> findByName(String name);   // 이름이 중복되면 터진다
```

`findById`처럼 PK로 찾는 건 항상 하나지만, PK가 아닌 컬럼으로 찾으면 여러 개가 나올 수 있다.
JPA는 여러 개를 단일 객체에 담을 방법이 없어서 예외를 던진다.

개발 중에는 데이터가 적어 하나만 나오다가, 데이터가 쌓이면서 뒤늦게 터지는 게 이 오류의 성격이다.

### 해결

의도에 따라 둘 중 하나를 고른다.

**여러 개가 나오는 게 정상이라면** 리스트로 받는다.

```java
List<Member> findByName(String name);
```

**하나만 나와야 하는 게 맞다면** 조건이 부족한 것이므로 조회 조건을 좁히거나, DB에 유니크 제약을 걸어 애초에 중복이 안 들어가게 막는다.

```java
@Column(unique = true)
private String email;
```

### 다시 겪지 않으려면

리턴 타입을 단일 객체로 쓸 때는 "이 조건이 정말 유일한가"를 한 번 확인하는 게 좋다.
유일하다고 생각한 근거가 코드가 아니라 **지금 들어 있는 데이터**라면, 언젠가는 터진다.

<br/>

## 정리

| 오류 | 진짜 원인 | 해결 |
|---|---|---|
| SQL Error 1064 | 엔티티·필드 이름이 DB 예약어와 충돌 | 식별자 인용 설정 또는 이름 변경 |
| cannot deserialize from Object value | Jackson이 쓸 기본 생성자가 없음 | `@NoArgsConstructor` 추가 |
| did not return a unique result | 단일 타입으로 받았는데 결과가 여러 개 | `List`로 받거나 조건·제약 보완 |

세 가지 모두 JPA와 Jackson이 자동으로 해주던 일이 내 코드의 전제와 어긋났을 때 생긴 문제였다.
자동으로 처리되는 구간일수록 무엇을 전제로 동작하는지 알아 두는 편이 결국 빠르다는 걸 알게 됐다.
